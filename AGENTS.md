# agent-serena-wrapper

Skill plugin that bundles a Serena MCP server (launched headless via `uvx`) alongside `skills/serena-wrapper/SKILL.md`. The Claude manifest (`.claude-plugin/plugin.json`) declares the server directly in its `mcpServers` block; the Codex manifest (`.codex-plugin/plugin.json`) instead points `mcpServers` at a separate root-level `codex-mcp.json` file (see the placeholder-expansion contract below for why) — either way the host agent starts it automatically. Claude Code loads the skill when its `description` matches the user's intent.

## Tool priority

Skills and MCP tools take priority over raw file tools — and this **explicitly overrides** the generic harness default that says "prefer the dedicated file/search tools (Glob/Grep/Read)". When a skill or MCP tool covers the task, reach for it first; fall back to raw Glob/Grep/Read only when none applies.

Concretely: any *"where is X defined / what does the code support / which Y exist / how does X work / find the callers of X"* question is a **code-understanding task → use the matching skill first** (e.g. the `serena-wrapper` symbol-aware tools), never raw Glob/Grep/Read.

## Contracts an agent won't infer from the tree

- **Release is orphan-branch + marketplace dispatch.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) stamps the version, then force-pushes an orphan `release` branch holding only install-ready files and POSTs a dispatch (`category: skill`) to `seretos-agents/modular-software-factory`. `main` and `release` share no history. Clients install at the tag `agent-serena-wrapper--vX.Y.Z`.
- **Required secret:** `MARKETPLACE_DISPATCH_TOKEN` — fine-grained PAT, `Contents: RW` + `Pull requests: RW` on `seretos-agents/modular-software-factory` only.
- **`assets/icon.png` is a release artifact, not just a repo file.** The dispatch payload sends a `raw.githubusercontent.com/${repo}/${TAG}/assets/icon.png` URL to the marketplace, so the file must live on the orphan `release` branch at the tagged commit — `release.yml`'s stage step copies `assets/` into the staging tree for exactly that reason. Ship `assets/icon.png` from day one or the marketplace listing has no image.
- **`description.md` is a release artifact too.** It is the richer, user-facing marketplace description (key features for the install decision) — distinct from the one-line `description` in the manifests. `release.yml` stages it onto the orphan `release` branch and the dispatch payload carries a `description_url` (`raw.githubusercontent.com/${repo}/${TAG}/description.md`). The marketplace dispatcher (`update-registry.yml`) stores the inline `description` and `description_url` as two independent registry fields (each preserved-on-omit like `icon`), so both are sent; keep `description.md` at the repo root or the raw URL won't resolve.
- **Marketplace tags are sent in the dispatch.** `release.yml`'s `client_payload` carries `"tags": ["coding"]` (JSON string list); the marketplace dispatcher reads `.tags // []`. Add/adjust tags there to change how the skill is categorized in the listing.
- **Depending on an MCP plugin:** declare it under `dependencies` in `.claude-plugin/plugin.json` (`{ "name": "agent-<mcp>", "version": ">=0.0.1 <1.0.0" }`); Claude Code installs/loads it automatically with this skill. Serena is wired directly via `mcpServers` in both manifests (not via `dependencies`), which is why `dependencies` stays `[]`.
- **Codex does not expand `${...}` placeholders in `args`, so its Serena declaration cannot use one.** `.claude-plugin/plugin.json` and `hooks/hooks.json` use `${CLAUDE_PLUGIN_ROOT}` (Claude-only, and Claude does expand it). Codex's declaration lives at root-level `codex-mcp.json` (mirroring OpenAI's own `codex-security` plugin shape) with `./`-relative `args` and `cwd: "."`; `.codex-plugin/plugin.json` points at it with `"mcpServers": "./codex-mcp.json"` rather than declaring the server inline. `cwd: "."` resolves to the plugin's own install directory, not the caller's workspace — Codex supplies no workspace hint at MCP-server spawn time — so the Codex declaration passes no `--project`/`--project-from-cwd` flag; the agent must call `activate_project` itself on first use (see `skills/serena-wrapper/SKILL.md`, "Codex: activate the project before first use"). `codex-mcp.json` is not named `.mcp.json`, because Claude Code auto-loads a plugin-root `.mcp.json` and would double-register `serena` with a Codex-shaped entry. Keep `command` a bare `node` (no placeholder) in both declarations. `.github/scripts/stage-tree.sh` — the single script both `release.yml`'s stage step and the local tests call — copies `codex-mcp.json` onto the staged/release tree the same way it copies the manifests. `scripts/codex-manifest.test.mjs` and `scripts/codex-handshake.test.mjs` (both run in `lint.yml`) guard this against the release-staged tree, not just the repo's working copy.
- **Release notes / changelog come from `src/<TAG>` markers on `main`.** The release tag sits on a parent-less orphan commit, so GitHub cannot diff it against anything; `release.yml` instead pushes a lightweight tag `src/agent-serena-wrapper--vX.Y.Z` at the `main` commit it releases from, generates the notes between `src/<previous tag>` and `src/<TAG>` (`releases/generate-notes`, written with `--notes-file`), and forwards the same body as `changelog` in the marketplace dispatch (omitted when empty). The `stamp` job (read-only token) checks everything first — default branch, `<TAG>` and `src/<TAG>` absent, `src/<previous tag>` present — so a failed check burns no version. The logic lives in `.github/scripts/{prev-release-tag,preflight-tags,marketplace-payload}.sh`, tested by `tests/test_release_scripts.py` (`release-scripts` job in `lint.yml`, ubuntu + windows; needs `jq`).
  **One-time bootstrap (a human, before the first release after this change):** the previous release has no marker yet, so `stamp` fails with these commands until it exists. Take `<head_sha>` from the `head_sha` of that release's successful `release.yml` run (`gh run list --workflow=release.yml --json databaseId,headSha,displayTitle,createdAt,conclusion`), then: `git tag src/agent-serena-wrapper--v0.1.4 <head_sha>` and `git push origin src/agent-serena-wrapper--v0.1.4`. That exact `head_sha` is the only accepted source; if the run metadata has aged out the marker cannot be bootstrapped this way and a human must decide. Never guess a commit (e.g. by commit time) — a wrong marker silently mis-scopes every later changelog.
